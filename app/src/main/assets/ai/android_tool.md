# Skill: android

The `android` skill inspects, navigates and tests native Android apps on this device through the VibeStudioAutomator companion app (AccessibilityService, works fully offline; Shizuku is an optional extra). It is lazy: load it with the skill-schema tool before use. It is offered only while VibeStudioAutomator is installed. The first use in a chat session asks the user for permission.

## Key Capabilities:
- `android_status`: Driver mode (ACCESSIBILITY | SHIZUKU | UNAVAILABLE), capabilities, allowlist and run state. Call it first.
- `android_begin_session` {package}: **Call first.** Declares the app under test; the Automator binds its window. Everything you see/do is window-relative (0,0 = the app's top-left corner) and nothing outside the window is reachable. `android_begin_full_device_session` is a separate, descriptor-less whole-screen mode (only when the user enabled Full Device Mode).
- `android_dump_ui_tree`: Compact UI tree of the foreground app; every node gets an integer `id` valid only for that dump.
- `android_tap_node`: Tap a node by `id` from the latest dump.
- `android_tap` / `android_swipe`: Gestures in native pixels. For `android_tap` with screenshot coordinates pass the screenshot's `scaleFactor`.
- `android_input_text`: Set text on a node (or the focused one if `id` is omitted).
- `android_global_action`: BACK, HOME, RECENTS or NOTIFICATIONS. HOME/RECENTS/NOTIFICATIONS leave the app box: use them only when the user asks.
- `android_launch_app`: Launch an app by package name (binds the session; adopts the open window if the package matches the session).
- `android_screenshot`: JSON with `base64`, `width`, `height`, `scaleFactor`; the image is at most 64 KB.
- `android_install_apk`: Installs an APK through the Automator's PackageInstaller (no Shizuku needed). The user must tap Install in the system dialog themselves: the call BLOCKS (agent loop paused) until they do; the frame is hidden and the screen unreadable meanwhile. Never try to tap the installer. Pass the absolute path of the APK inside the IDE home (e.g. ~/Project/bin/App.apk); the IDE streams it to the Automator via ParcelFileDescriptor. NEVER copy the APK to /sdcard or shared storage first: it is not available and will not work.
- `android_logcat` (optional `package`, `level`): whole-device log needs Shizuku or `pm grant dev.vibestudio.automator android.permission.READ_LOGS`; otherwise only the Automator's own log. `android_force_stop`: Shizuku, otherwise killBackgroundProcesses.
- `android_emergency_stop`: Stops the session immediately.

## Android Tool Rules & Best Practices
1. **UI tree first, screenshot rarely**: `android_dump_ui_tree` is the default way to observe. It gives exact text, ids, bounds and state (clickable, editable), so taps via `android_tap_node` and typing via `android_input_text` with an `id` are precise, while coordinates guessed from an image are not. Use the dump to find controls, read text, check results, confirm a screen changed and fill forms. A large dump (LinkedIn, feeds, Compose, 25 KB+) is still better than an image: look only at the nodes you need (`text`, `desc`, `bounds`) and scroll with `android_swipe` when the target is off screen. Take a screenshot only when (a) the dump is truncated and the target is not in the visible part, (b) the dump is empty or shows no useful nodes (canvas, images, WebView), or (c) visual state matters and the tree cannot tell it. For critical actions (send, submit, delete, pay, confirm), read the dump right before the action to confirm the target node and its text, and read it again right after to confirm the result; add one screenshot only if the dump is ambiguous. If an action returns `ok:false` or nothing changed, dump again and retry with a node id before taking any screenshot. Never observe the same unchanged screen twice.


2. **Ids are per dump**: Node ids change whenever the screen changes. Dump again after every action that changes the UI.
3. **Coordinates are window-relative**: screenshot pixels, `bounds` in the UI tree and `android_tap` / `android_swipe` all use the same coordinates, relative to the app window (also for a floating `quarter` window). Real pixel = screenshot coordinate / `scaleFactor`. Prefer `android_tap_node`; otherwise tap the center of a node's `bounds` (or a screenshot point) directly; never add a window offset yourself.
3a. **Fresh screens load**: right after launch or a tab switch the tree/screenshot may show a skeleton or spinner. Dump again once before concluding anything.
4. **Scope**: Only packages on the user's allowlist can be tapped or typed into. If an action fails, check `android_status` for the allowlist instead of retrying blindly.
5. **Errors**: Error 10 = the user paused the agent; 15 = the user stopped it. Do not retry; tell the user and call `task_complete`.
6. **Respect the user**: The user can pause or stop you from the Automator bubble at any time. Never work around this.
7. **Permission / Settings screens**: If a tool error starts with `PERMISSION_REQUIRED` (or the Automator opened a system Settings screen), stop working immediately: do not tap or type in Settings or other system screens, press BACK once to leave them, then call `task_complete` asking the user to grant the permission manually and re-run the task.
8. **Session**: The Automator frame and bubble stay visible for the whole task and are removed by the IDE when you call `task_complete`. Always finish with `task_complete`.
9. **Clean up apps you opened**: Unless the user said otherwise, before `task_complete` close every app you launched yourself with `android_force_stop`, and bring the user back to VibeStudio (`android_launch_app` with the IDE package, or BACK/HOME). Never close apps the user had open before you started. Without Shizuku `android_force_stop` fails (missing KILL_BACKGROUND_PROCESSES): do not retry, tell the user the app is still open.
10. **Floating window (`quarter`) is the DEFAULT way to launch apps**: always pass `quarter: "top_right"` (or another quarter, e.g. `top_left`) to `android_launch_app` when freeform is available (`android_status` shows `freeform:true`), so the user keeps the IDE chat visible; fall back to a normal full-screen launch only if freeform is unavailable or the user asks otherwise. Works without Shizuku. Launching an app that is already running just brings its existing window back to the front (no second instance). The app's window belongs to this chat session: launch it once, then keep working in that window; do not call `android_launch_app` again unless it was closed. The user may interact with it too (open a DM, navigate, type): dump the tree again before acting and continue from the state you find, never reset it. The first freeform launch may show a system tutorial overlay (e.g. Motorola) that the user must dismiss. `ok:true` only means the activity started; verify with one dump.
11. **Shortcuts**: prefer existing UI shortcuts (bottom tabs, recent searches, saved filters) over typing. Keep tool calls sequential when each depends on the previous screen; batch only independent reads.
12. **Testing VibeStudio itself**: never build/install the release id `com.vibestudio.app` (it replaces the IDE you run in). Build the debug variant with `APP_ID=com.vibestudio.dev ./build.sh`, install it with `android_install_apk`, launch `com.vibestudio.dev` with `quarter: "top_right"` and test from this chat. Do it autonomously after UI changes; do not ask the user to install manually.
