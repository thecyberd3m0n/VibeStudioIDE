# Agent loop completion & system-prompt slimming — plan

> Living document: every consecutive prompt in this effort must update this file (context, findings, decisions, task status).

## Context (reported 2026-11-08)

During a long multi-step task (a project scaffold started via a long-running CLI command) the loop ended on a text-only reply:
"The ... setup procedure is still in progress (...) Let me know if you'd like further updates or assistance".
The job was not finished, but the loop stopped. (The task itself is only an example validation task; the fix must be task-agnostic: any task a developer runs - new app in any stack, bug fix in an existing app, etc.)

Problems:
1. **Premature loop break.** The agent must keep going until the task is really done (or it needs the user).
2. **`system_instruction.md` is too big** and duplicates terminal guidance that already lives in the per-tool prompt `terminal_tool.md`. System instruction should hold only cross-cutting rules.

## Findings so far

### How the loop stops today
- [AgentLoopController.java](app/src/main/java/com/vibestudio/app/chat/session/AgentLoopController.java): `STOP_GUARD` is appended to the system instruction; a text-only reply gets a `NUDGE_MESSAGE` up to `MAX_CONSECUTIVE_NUDGES = 2` times, then the loop gives up (`FINISHED`). `DEFAULT_MAX_TURNS = 50`.
- Nudge counting is in `ChatSession` (~line 468). A long-running `ng new` / `npm install` makes the model write "still in progress" 3 times in a row, which exhausts the nudges, so the loop ends although the work is unfinished.
- Hypothesis: after an async command the model has no tool call to make "while waiting", so it emits prose. The nudge doesn't tell it what to do (e.g. `read_terminal_output` with a delay).

### How big is the VS Code system instruction? (`~/src/vscode`)
- The VS Code agent-host code ([prompts/](/home/tcd/src/vscode/src/vs/platform/agentHost/node/copilot/prompts)) does **not** contain the full prompt. It uses `@github/copilot-sdk` `SystemMessageConfig` in `customize` mode: the SDK foundation prompt is kept and VS Code only overrides named sections.
- The part VS Code itself owns is tiny:
  - `identity`: 1 sentence (~280 chars) in `systemMessage.ts`.
  - `tool_instructions`: a list of one-line, **gated** nudges (`TOOL_INSTRUCTION_LINES` in `toolInstructions.ts`); a line is only included if the relevant tool exists in the session.
  - Per-model optional overrides: Opus 4.8 `tone` (~130 chars) + 2 `guidelines` lines; OpenAI `code_change_rules` (3 lines).
- The foundation prompt itself ships inside the closed Copilot runtime binary (`~/.cache/copilot/pkg/.../runtime.node`), assembled from fragments at runtime. Its exact size can't be measured reliably from the binary and it is not in the VS Code source.
- Design takeaways to copy: (a) section-based prompt, (b) per-tool guidance is **gated on the tool being present**, (c) per-model overrides are small and opt-in, (d) explicitly *no* "progress scaffolding" for strong models.
- Note: `planned_delay_ms` is a VibeStudio-specific mechanism (not in VS Code). It was designed to avoid wasting tokens on polling; keep it (see CHANGELOG 0.1.x). Template restored with sync (0) and async (5000) examples in a previous change.

### Native tools vs text protocol (`supportsNativeTools()`) - findings
- Native today: Gemini, GitHub Copilot (declare `tools`, receive structured calls). Text protocol: OpenAI, Claude (ignore `tools`; model writes `{"tool","args"}` JSON in prose, parsed by `ToolExecutionManager`).
- Both converge early: native providers convert the structured call into the same `{"planned_delay_ms","tool","args"}` JSON text (`AbstractAiProvider.toolCallContent`), so parsing/execution/UI are shared.
- Differences still open: native providers send history back as plain text (assistant JSON text + "user" tool results), not as native `tool_calls`/`tool` role messages; only the first `tool_calls` entry is used (parallel calls dropped).
- Planned: flag decides prompt assembly (native: slim prompt + guidelines-only injection; text: catalog + `get_skill_schema` + full schemas + format section). Consider per-model capability and runtime downgrade to text protocol if the API rejects `tools`. OpenAI and Claude APIs support native function calling, so migrating them is a follow-up.

### Native tool calling rollout - risk list (2026-11-08)
Context: native transport is already live for Gemini and Copilot (chat completions + responses); what is left is consuming the flag (prompt split, guidelines-only injection, router accessor). Text mode must keep working for OpenAI/Claude and for any model reporting `tool_calls=false`.
1. **Downgrade vs slim prompt (highest):** the existing HTTP-400 retry resends the same system prompt without `tools`. With a native-slim prompt (no schemas) the retried model has neither declared tools nor schemas. The downgrade must rebuild the prompt in text mode (and be remembered per model, otherwise every turn pays a failed request + retry).
2. **Parallel tool calls dropped** (device data: all 28 Copilot models on this account report `parallel_tool_calls=true`, so models WILL emit several calls per turn; it is a separate flag from `tool_calls` in the API, and not guaranteed for other accounts/providers): all native paths use only the first call (`tool_calls[0]` / first `functionCall` / first `function_call`); extra calls are lost silently. Mitigate: log dropped calls, tell the model one call per response, or execute all later.
3. **Agent tool restrictions:** `AgentToolPolicy` is enforced only at execution; native mode declares every tool, so a restricted agent sees tools it cannot use. Filter `getActiveTools()` by the active agent's policy.
4. **Keep the text parser:** history is plain text (assistant JSON text, tool results as user text), so models may still emit JSON in prose; `ToolExecutionManager` fallback must stay.
5. **Flag evaluated per turn/model:** model switch mid-chat or a runtime downgrade must change the mode on the next turn; history from both modes is compatible because native calls are converted to the same JSON text.
6. **Catalog and custom skills/agents:** they are not tools; keep the catalog + loaded-skill injection in native mode (only built-in skill *schemas* are dropped). Existing scenario tests assert catalog/skill text in the system prompt.
7. **Token cost:** ~7.5 KB (~2-3K tokens) of tool definitions go out on every native request, so lazy loading saves nothing in native mode; compare total prompt size before/after.
8. **Schema validity per API:** one invalid tool schema (Gemini accepts only an OpenAPI subset; names must match `[A-Za-z0-9_-]{1,64}`) 400s the whole request; validate schemas in tests.
9. **Native history later:** Gemini 3 function calls carry thought signatures that must be echoed if native history is adopted; not an issue while history stays text.
10. **Tests:** providers default to `supportsNativeTools()=false`, so existing scenario tests stay in text mode; add native-mode tests for prompt assembly.

### Native history format (design, 2026-11-08; not implemented)
Today every provider gets history as plain role/text: a tool call is an assistant message containing our JSON text, a result is a *user* message. Native format keeps structure so the API (and the model's training) recognizes calls and results.
- **Data model:** `ChatMessage` has only `toolName`/`toolArgs`. Needs a stable `callId` (provider-issued when native, generated when text) on both the call and its result, plus a "turn group" so several calls from one reply stay together (one assistant message with N calls, then N results). Providers can then project the same history either way (native or text), which also keeps the text-mode fallback and mid-chat model switches working.
- **Chat Completions (Claude/Gemini/Kimi/GPT-4 via Copilot):** assistant message `{role:assistant, content, tool_calls:[{id, type:function, function:{name, arguments:"<json string>"}}]}` followed by one `{role:tool, tool_call_id:id, content:"<result>"}` per call. Every `tool_calls` id must be answered by a `tool` message, in the same position, or the API 400s; kimi-k3 uses its own id style (VS Code special-cases it).
- **Responses (gpt-5.x/6.x, grok, mai):** `input` items `{type:function_call, name, arguments, call_id}` and `{type:function_call_output, call_id, output}`. For reasoning models with `store:false` the previous `reasoning` items (`encrypted_content`, requested via `include:["reasoning.encrypted_content"]`) must be replayed next to their function_call, or some models degrade/error; VS Code does this (`responsesApi.ts`).
- **Gemini native API:** model turn with `functionCall` parts, then a user-role turn with matching `functionResponse` parts (one per call, same order). Gemini 3 attaches `thoughtSignature` to function-call parts and expects it echoed back, otherwise 400 (VS Code's `geminiMessageConverter.ts` carries it as a pending signature) - so the raw provider parts/signature must be stored with the assistant message.
- **What must be stored per assistant turn (provider-opaque blob):** raw reasoning items (Responses), thought signatures (Gemini), call ids. Our UI messages stay as they are; the blob rides along and is only read by the provider that produced it. Switching provider mid-chat => fall back to text projection of older turns.
- **Constraints to handle:** (1) pairing integrity: `HistoryCompressor` (and any trimming) must never drop a call without its result or vice versa; today it collapses to a TOOL_RESULT summary; (2) results over the 25 KB truncation still need valid pairs; (3) an interrupted/stopped turn leaves a call without a result -> synthesize a "cancelled" result (VS Code uses `MISSING_STATEFUL_TOOL_RESULT` for the same reason); (4) after a downgrade to text mode, calls become JSON text again.
- **Why do it:** models are trained on the native shape (better call accuracy, no JSON-in-prose), prompt caching works better with stable structure, and Gemini 3 / reasoning models need the replayed signatures/reasoning for best quality. Not required for correctness today, so it is an upgrade, not a bug fix.
- **Suggested order:** 1 `callId` + group in `ChatMessage` and the session (no provider change); 2 Copilot chat-completions projection (simplest, covers Claude); 3 Responses (call items + reasoning replay); 4 Gemini (functionResponse + thoughtSignature); 5 compressor pairing safety.

### Native history - IMPLEMENTED (2026-11-08; built + installed, awaiting manual test; unit tests written, NOT run or compiled)
- **Data model:** `ChatMessage.withToolLink(callId, turnId, state, stateKind)` (+ getters). Every tool call/result message the session stores is linked: call id from the API (native) or generated (`call_<24 hex>` in text mode), one `turnId` per model reply, and a provider-specific replay `state` on the call message only. `AiResponse.ToolCall{id, call, state, stateKind}` / `getToolCalls()` carry structured calls from providers; `content` still holds the JSON text (text-mode fallback, logs).
- **Projection:** `provider/NativeHistory.project(history, nativeTools, requiredKind)` -> items USER / ASSISTANT / ASSISTANT_CALLS / TOOL_RESULT. Groups the stored `[call][result][call][result]` pairs of one turn into one assistant item + results in call order; synthesizes a result for a call without one; leaves orphan results and unlinked messages as text; a requested delay goes back in as the `planned_delay_ms` argument. Without native tools everything stays text exactly as before. OpenAI/Claude providers are untouched.
- **Copilot chat completions:** assistant `tool_calls` (omits `content`), `role:tool` + `tool_call_id` replies, Kimi id formats (`functions.name:N` / `name:N` for k3, as VS Code). **Responses:** `function_call` / `function_call_output` items, `message` items with `input_text`/`output_text` parts (VS Code shape), reasoning items (`type,id,summary:[],encrypted_content` only) replayed in front of their calls and ONLY to the model that produced them. **Gemini:** raw `functionCall` parts replayed exactly (thought signature kept) answered by one user turn of `functionResponse` parts (`response:{result|error}`, `id` echoed only when the API issued one; roles per Google's reference: only user/model), and only for calls Gemini itself produced; anything else (other provider / text mode) stays text, so no missing-signature 400.
- **Safety:** `HistoryCompressor` moves its cut back so a kept result never loses its call. Calls beyond the parallel cap or after `task_complete` are not in the history, so the projected assistant item only lists recorded calls (pairs always match). After a downgrade to text mode the same history is simply projected as text.
- **Not measured / honest note on tokens:** native structure is mainly about reliability (no JSON-in-prose, correct pairing, reasoning/thought-signature continuity) and stable prefixes for provider caching. It does NOT shrink the history by itself: a structured call costs about the same as our JSON text, and replayed Responses reasoning adds input tokens. Compare `usedTokens` per turn before/after on the device to see the real effect.
